# Another Cycle

**Complete development cycle from orientation to evolution.**

Orchestrates all major workflows into a single comprehensive master workflow: onboard → explore → check-assumptions → hypothesis → critique → comprehensive-orchestration → analyze → engineer → improve → version-bake → run-it → prove-it → evolve → journal → next → goal → checkpoint.

**Use when:** Starting major new work, need complete systematic approach, want full cycle from onboarding through quality assurance and evolution.

---

## Purpose

This command provides:
- **Complete Orientation**: Full onboarding and exploration
- **Comprehensive Analysis**: Assumption validation, hypothesis formation, critique, orchestration
- **Full Engineering**: Complete engineering workflow
- **Quality Assurance**: Improvements, version-bake, run-it, proof
- **Evolution**: Being evolution from Source
- **Reflection**: Journal and learning capture
- **Planning**: Next steps, goals, checkpoints

---

## Philosophy

### 1. Complete Lifecycle Coverage

The workflow covers the entire development lifecycle:
- **Orientation**: Get oriented and understand the codebase
- **Analysis**: Validate assumptions, form hypotheses, critique, orchestrate
- **Engineering**: Plan and implement systematically
- **Quality**: Improve, verify, and prove quality
- **Evolution**: Track Being evolution and genetic lineage
- **Planning**: Identify next steps and track goals

### 2. Systematic Progression

Each phase builds on the previous:
- Orientation provides foundation for analysis
- Analysis informs engineering decisions
- Engineering creates work for quality assurance
- Quality ensures evolution is meaningful
- Evolution captures learnings for future cycles

### 3. Evidence-Based Throughout

Every phase produces evidence:
- Assumptions validated with traces
- Hypotheses verified with evidence
- Decisions supported by data
- All findings documented and traceable

### 4. Self-Correcting Balance

The workflow includes self-correcting mechanisms:
- Deep analysis before critique (prevents being too harsh)
- Multiple verification points (ensures accuracy)
- Reflection after work (captures learnings)
- Evolution tracking (preserves genetic lineage)

## Workflow Sequence

The command executes 17 phases organized into 6 logical groups:

### Group 1: Orientation & Setup

**Phase 1: `/onboard`**
- Standard repository onboarding
- Proceed → spin-up → analyze → phase1 → prepare → recap
- Get oriented to the project
- Initial analysis and setup

**Phase 2: `/explore`**
- Deep codebase exploration
- Structure, architecture, patterns, dependencies
- Key functionality mapping
- Integration points identification

**Time Estimate**: ~10-15 minutes

---

### Group 2: Analysis & Planning

**Phase 3: `/check-assumptions`**
- Identify and validate all assumptions
- Categorize by type and risk
- Gather evidence from multiple sources
- Generate validation report with traces

**Phase 4: `/hypothesis`**
- Form testable hypotheses based on findings
- Identify supporting/contradicting evidence
- Define verification plan
- Assess confidence level

**Phase 5: `/critique`**
- Security-first adversarial review
- Find vulnerabilities, assumptions, overengineering
- Prioritize by severity (CRITICAL first)
- Generate critique report

**Phase 6: `/comprehensive-orchestration`**
- Full orchestration workflow (prompt template)
- Spin-up → consider → engineer → visualize → analyze → goal → checkpoint → execute → hypothesis → verify → reflect → recap → proceed → decide
- Complete strategic planning
- **Note**: This is a prompt template, not an executable command - execute phases manually or use individual commands

**Phase 7: `/analyze`**
- Data analysis, insights, and action planning
- Health analysis
- Issue identification
- Opportunity discovery
- Pattern analysis
- Prioritized action plan

**Time Estimate**: ~60-90 minutes

---

### Group 3: Engineering & Implementation

**Phase 8: `/engineer`**
- Complete engineering workflow
- Spin-up → explore → draft plan → critique plan → finalize plan → begin
- Systematic implementation approach
- Active tool usage (Empirica, _pyrite, GitHub MCP, work-efforts)

**Time Estimate**: ~45-80 minutes

---

### Group 4: Quality Assurance

**Phase 9: `/improve`**
- Identify and prioritize improvements
- Code quality, documentation, architecture, testing, performance, usability
- Score-based ranking
- Actionable recommendations

**Phase 10: `/version-bake`**
- Complete quality workflow
- Reflect → run-it → improve → check-assumptions → verify → hypothesis → prove-it
- Tracks genetic lineage of ideas
- Self-correcting loop

**Phase 11: `/run-it`**
- Comprehensive workflow orchestration (15 phases)
- Consider → think → check-assumptions → deep-analyze → critique → status → hypothesis → prove-it → verify → proceed → reflect → checkpoint → decide → next → goal
- Self-correcting balance

**Phase 12: `/prove-it`**
- Prove scientific method tool works
- Run simple and real experiment proofs
- Show state capture (A & B) and data collection (C)
- Verify file persistence

**Time Estimate**: ~60-110 minutes

---

### Group 5: Evolution & Reflection

**Phase 13: `/evolve`**
- Spawn new Being from Source
- Run complete version-bake workflow
- Track genetic lineage from Source outward and back
- Document Being evolution

**Phase 14: `/journal`**
- AI journal system hub
- View recent entries, search, statistics
- Write new reflections
- Capture learnings

**Time Estimate**: ~60-115 minutes

---

### Group 6: Planning & Tracking

**Phase 15: `/next`**
- Identify next step based on goals
- Analyze active goals, work in progress, context
- Prioritize by importance and urgency
- Provide actionable recommendation

**Phase 16: `/goal`**
- Track larger goals and break into steps
- Review current goals
- Update progress
- Create new goals if needed

**Phase 17: `/checkpoint`**
- Create situation report and status update
- Recap conversation
- Document current state
- Update devlog and work efforts

**Time Estimate**: ~5-10 minutes

## Configuration Options

### `--quick`
Skip non-essential phases for faster execution:
- Skips comprehensive-orchestration (uses shorter analysis)
- Skips evolve (no Being evolution)
- Skips some reflection phases
- Focuses on core workflow

**Example**: `/another-cycle --quick`

---

### `--focus <area>`
Focus on specific area:
- `orientation` - Only Group 1 (onboard, explore)
- `analysis` - Only Group 2 (check-assumptions, hypothesis, critique, comprehensive-orchestration, analyze)
- `engineering` - Only Group 3 (engineering)
- `quality` - Only Group 4 (improve, version-bake, run-it, prove-it)
- `evolution` - Only Group 5 (evolve, journal)
- `planning` - Only Group 6 (next, goal, checkpoint)

**Example**: `/another-cycle --focus quality`

---

### `--skip <phases>`
Skip specific phases (comma-separated):
- List phase numbers or names to skip
- Useful for customizing workflow

**Example**: `/another-cycle --skip "evolve,journal"`

---

### `--phases <list>`
Run only specified phases (comma-separated):
- List phase numbers or names to run
- Useful for custom workflows

**Example**: `/another-cycle --phases "onboard,explore,check-assumptions"`

## Error Handling

If any phase fails:

1. **Document the Failure**:
   - Note which phase failed
   - Document error message
   - Capture context at time of failure

2. **Continue if Possible**:
   - Skip failed phase if not critical
   - Continue with remaining phases
   - Note what was skipped

3. **Provide Summary**:
   - List completed phases
   - List failed phases
   - Note partial completions

4. **Suggest Remediation**:
   - Provide steps to fix failure
   - Suggest alternative approaches
   - Recommend when to retry

**Graceful Degradation**: The command continues with available phases even if some fail. Critical phases may cause subsequent phases to skip, but non-critical failures shouldn't stop the entire cycle.
