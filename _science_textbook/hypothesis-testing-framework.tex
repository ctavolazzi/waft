\chapter*{Preface}

This textbook documents the design and implementation of a hypothesis testing framework that enables iterative scientific method execution with real-time visualization. The work presented here emerged from a systematic investigation of existing scientific method infrastructure and the design of a consensus mechanism for determining when sufficient evidence has been gathered to reach a verdict on a hypothesis.

The framework combines established scientific method principles with modern software architecture, creating a system where artificial intelligence can test hypotheses iteratively, with each experiment contributing to an evolving consensus. The consensus mechanism uses weighted confidence calculations to determine when sufficient agreement has been reached among multiple experimental runs.

This book is organized to guide readers through the complete process: from understanding the existing scientific method infrastructure, through the design of consensus algorithms, to the implementation of real-time visualization systems. Each chapter builds upon the previous, providing both theoretical foundations and practical implementation details.

The content is derived from actual development conversations and codebase investigations, making this both a theoretical exploration and a practical guide for implementing similar systems.

\chapter{Introduction to Hypothesis Testing Systems}

\section{The Problem Statement}

The goal is to create a testing framework and user interface where artificial intelligence can solve hypotheses iteratively over time using the scientific method. The system should:

\begin{itemize}
    \item Display the hypothesis prominently at the top of the interface
    \item Run multiple instances of scientific method loops to collect data, observe, and report
    \item Show progress in real-time as experiments execute
    \item Determine when consensus has been achieved among experiments
    \item Bubble the verdict up the chain once consensus is reached
    \item Provide a clear answer to the hypothesis question in the UI
    \item Allow users to halt experiments at any time
\end{itemize}

\section{System Requirements}

The framework must support:

\begin{enumerate}
    \item \textbf{Iterative Experimentation}: Multiple experiments running sequentially, each following the complete scientific method cycle
    \item \textbf{Real-Time Visualization}: Live updates showing experiment progress, data collection, and analysis results
    \item \textbf{Consensus Determination}: A mechanism to determine when sufficient evidence has been gathered
    \item \textbf{User Control}: Ability to start, pause, and halt experiments
    \item \textbf{Evidence Aggregation}: Combining results from multiple experiments into a coherent verdict
\end{enumerate}

\section{Architecture Overview}

The system architecture consists of three main components:

\begin{description}
    \item[Backend] Python-based scientific method tool with consensus engine and experiment runner
    \item[API Server] FastAPI server providing REST endpoints and WebSocket support for real-time updates
    \item[Frontend] Electron desktop application with React UI for visualization
\end{description}

\section{Analysis System Limitations}

The existing \texttt{ExperimentAnalyzer.analyze\_iteration\_results()} method provides basic aggregation:

\begin{itemize}
    \item Counts verified vs. refuted experiments
    \item Calculates simple average confidence
    \item Uses majority voting (verified\_count > refuted\_count)
    \item Does not implement weighted confidence consensus
    \item Does not check for consensus criteria (minimum experiments, agreement threshold)
\end{itemize}

This basic analysis is insufficient for determining true consensus, necessitating the design of a more sophisticated consensus engine.

\chapter{Consensus Algorithm Design}

\section{The Need for Consensus}

Simple majority voting is insufficient for scientific hypothesis testing. A more sophisticated approach is needed that:

\begin{itemize}
    \item Accounts for confidence levels in individual experiments
    \item Requires sufficient evidence before making a verdict
    \item Prevents premature conclusions from small sample sizes
    \item Provides clear criteria for when consensus is achieved
\end{itemize}

\section{Weighted Confidence Consensus Algorithm}

\subsection{Core Principles}

The weighted confidence consensus algorithm is based on three principles:

\begin{enumerate}
    \item \textbf{Weighted Aggregation}: Experiments with higher confidence contribute more to the final verdict
    \item \textbf{Minimum Evidence}: A minimum number of experiments must be completed before consensus can be determined
    \item \textbf{Agreement Threshold}: A sufficient percentage of experiments must agree on the same verdict
\end{enumerate}

\subsection{Algorithm Specification}

The consensus calculation proceeds as follows:

\begin{enumerate}
    \item \textbf{Minimum Requirement Check}: If fewer than 3 experiments have completed, return \texttt{INCONCLUSIVE}

    \item \textbf{Weighted Confidence Calculation}:
    \begin{equation}
        \text{weighted\_confidence} = \frac{\sum_{i=1}^{n} \text{confidence}_i^2}{\sum_{i=1}^{n} \text{confidence}_i}
    \end{equation}

    Where the weight for each experiment is its own confidence value. This gives more weight to high-confidence experiments.

    \item \textbf{Verdict Counting}: Count experiments by their verification status:
    \begin{itemize}
        \item \texttt{verified\_count}: Experiments where \texttt{hypothesis\_verified = True}
        \item \texttt{refuted\_count}: Experiments where \texttt{hypothesis\_verified = False}
        \item \texttt{inconclusive\_count}: Experiments where \texttt{hypothesis\_verified = None}
    \end{itemize}

    \item \textbf{Consensus Criteria}: All of the following must be met:
    \begin{itemize}
        \item Weighted confidence > 0.75 (75\%)
        \item At least 70\% of experiments agree on the same verdict (verified OR refuted)
        \item Inconclusive experiments < 30\% of total
    \end{itemize}

    \item \textbf{Verdict Determination}:
    \begin{itemize}
        \item If \texttt{verified\_count / total >= 0.7} AND \texttt{weighted\_confidence > 0.75}: \texttt{VERIFIED}
        \item If \texttt{refuted\_count / total >= 0.7} AND \texttt{weighted\_confidence > 0.75}: \texttt{REFUTED}
        \item Otherwise: \texttt{INCONCLUSIVE} (continue running experiments)
    \end{itemize}
\end{enumerate}

\subsection{Algorithm Implementation}

\begin{lstlisting}[language=Python, caption=Consensus Engine Algorithm, label=lst:consensus-algorithm]
def calculate_consensus(
    experiments: List[ExperimentResult]
) -> ConsensusResult:
    """Calculate consensus from experiment results."""

    # Minimum requirement
    if len(experiments) < 3:
        return ConsensusResult(
            verdict="INCONCLUSIVE",
            confidence=0.0,
            experiment_count=len(experiments)
        )

    # Weighted confidence calculation
    total_weight = sum(e.confidence for e in experiments)
    weighted_sum = sum(
        e.confidence * e.confidence
        for e in experiments
    )
    weighted_confidence = (
        weighted_sum / total_weight
        if total_weight > 0 else 0.0
    )

    # Count verdicts
    verified = sum(
        1 for e in experiments
        if e.hypothesis_verified is True
    )
    refuted = sum(
        1 for e in experiments
        if e.hypothesis_verified is False
    )
    inconclusive = sum(
        1 for e in experiments
        if e.hypothesis_verified is None
    )
    total = len(experiments)

    # Consensus criteria
    # Check that inconclusive experiments < 30% (as per requirements)
    if inconclusive / total >= 0.3:
        return ConsensusResult(
            verdict="INCONCLUSIVE",
            confidence=weighted_confidence,
            experiment_count=total
        )

    if verified / total >= 0.7 and weighted_confidence > 0.75:
        return ConsensusResult(
            verdict="VERIFIED",
            confidence=weighted_confidence,
            experiment_count=total
        )
    elif refuted / total >= 0.7 and weighted_confidence > 0.75:
        return ConsensusResult(
            verdict="REFUTED",
            confidence=weighted_confidence,
            experiment_count=total
        )
    else:
        return ConsensusResult(
            verdict="INCONCLUSIVE",
            confidence=weighted_confidence,
            experiment_count=total
        )
\end{lstlisting}

\section{Why Weighted Confidence?}

The weighted confidence approach is superior to simple averaging because:

\begin{itemize}
    \item \textbf{High-confidence experiments matter more}: An experiment with 95\% confidence should influence the verdict more than one with 50\% confidence
    \item \textbf{Reduces impact of low-quality experiments}: Low-confidence experiments contribute less to the final decision
    \item \textbf{Reflects scientific practice}: In real science, well-designed, high-confidence experiments are given more weight
    \item \textbf{Prevents dilution}: Simple averaging can be skewed by many low-confidence experiments
\end{itemize}

\section{Data Flow}

The data flows through the system as follows:

\begin{enumerate}
    \item User inputs hypothesis via Electron UI
    \item UI sends \texttt{POST /hypothesis/start} to API server
    \item API server creates \texttt{ExperimentRunner} instance
    \item \texttt{ExperimentRunner} starts \texttt{ExperimentLoop.run\_iterative\_experiment()}
    \item Each experiment runs through scientific method cycle:
    \begin{itemize}
        \item Capture initial state (A)
        \item Run experiment, collect data (C)
        \item Capture final state (B)
        \item Analyze results
    \end{itemize}
    \item After each experiment, \texttt{ConsensusEngine} calculates consensus
    \item Results and consensus status broadcast via WebSocket
    \item Electron UI receives updates and displays in real-time
    \item When consensus reached, verdict bubbles to top of UI
\end{enumerate}

\chapter{Implementation Details}

\section{Halt Mechanism}

The halt mechanism allows users to stop experiments gracefully:

\begin{enumerate}
    \item User clicks halt button in UI
    \item UI sends \texttt{POST /hypothesis/halt} to API server
    \item \texttt{ExperimentRunner} sets \texttt{halt\_flag = True}
    \item \texttt{ExperimentLoop} checks halt flag between iterations
    \item Current experiment completes, but no new experiments start
    \item State saved, results preserved
\end{enumerate}

\chapter{Testing and Validation}

\section{Testing Scenarios}

The system should be tested with various scenarios:

\begin{enumerate}
    \item \textbf{Clear Verification}: 3+ experiments all verify hypothesis → consensus reached quickly
    \item \textbf{Clear Refutation}: 3+ experiments all refute hypothesis → consensus reached quickly
    \item \textbf{Mixed Results}: Experiments with mixed results → no consensus, continues running
    \item \textbf{Low Confidence}: Experiments with low confidence → no consensus until confidence improves
    \item \textbf{Halt Mid-Experiment}: User halts during experiment run → graceful stop
    \item \textbf{WebSocket Disconnection}: Client disconnects and reconnects → state recovery
\end{enumerate}

\section{Validation Criteria}

The system is considered successful when:

\begin{itemize}
    \item Consensus algorithm correctly identifies when sufficient evidence exists
    \item Real-time updates appear in UI within 1 second of experiment events
    \item Halt mechanism stops experiments gracefully without data loss
    \item Verdict bubbles to top when consensus achieved
    \item System handles edge cases (single experiment, all inconclusive, etc.)
\end{itemize}

\chapter{Conclusion and Future Work}

\section{Summary}

This textbook has documented the design and implementation of a hypothesis testing framework that enables iterative scientific method execution with real-time visualization. Key contributions include:

\begin{itemize}
    \item Weighted confidence consensus algorithm for determining when sufficient evidence exists
    \item Architecture for real-time experiment visualization
    \item Integration of existing scientific method infrastructure with new consensus mechanisms
    \item Design for Electron-based desktop application with WebSocket real-time updates
\end{itemize}

\section{Future Enhancements}

Potential future improvements include:

\begin{enumerate}
    \item \textbf{Experiment Result Visualization}: Charts and graphs showing data trends across experiments
    \item \textbf{PDF Export}: Generate scientific reports from experiment results using existing PDF generator
    \item \textbf{Session Persistence}: Save and load hypothesis testing sessions
    \item \textbf{Experiment Configuration UI}: Visual interface for configuring variable ranges and iteration counts
    \item \textbf{Integration with Science Bitch}: Connect with existing \texttt{/science-bitch} command workflow
    \item \textbf{Multi-Hypothesis Testing}: Support for testing multiple related hypotheses simultaneously
    \item \textbf{Statistical Analysis}: Advanced statistical tests (t-tests, ANOVA, etc.) for hypothesis validation
\end{enumerate}

\section{Lessons Learned}

The investigation and design process revealed several important insights:

\begin{itemize}
    \item \textbf{Systematic Investigation is Essential}: Understanding existing infrastructure before building new components prevents reinventing the wheel
    \item \textbf{Consensus is Different from Analysis}: Consensus determination requires different logic than simple result aggregation
    \item \textbf{Weighted Confidence is Superior}: Giving more weight to high-confidence experiments produces better verdicts
    \item \textbf{Real-Time Updates Require Careful Design}: WebSocket architecture must handle disconnections, reconnections, and state synchronization
    \item \textbf{User Control is Critical}: Ability to halt experiments provides necessary user agency
\end{itemize}
